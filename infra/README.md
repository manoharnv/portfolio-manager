# Infrastructure — Operator Runbook

This is the runbook for everything under `infra/` and `.github/workflows/`:
a dedicated GCP project, one e2-micro VM with a reserved static IP running
two isolated systemd units (`pm-backend`, `pm-strategy`), Caddy for TLS,
Firebase (Firestore/Auth/FCM/Functions), and the CI/CD around all of it.
Read [docs/08-infrastructure.md](../docs/08-infrastructure.md) first if you
haven't — this document is the "how," that one is the "what/why."

Every command below uses **placeholders** in `<ANGLE_BRACKETS>`. Nothing in
this repo contains a real project id, domain, email, or secret value
(docs/00 §0.7) — copy commands out, then substitute your own values in your
shell, not in the repo.

**A note on tooling**: this repo does not commit a `.terraform.lock.hcl`.
Run your own `terraform init` (or `tofu init`) once to generate one for your
machine/CI's toolchain and commit that — a lock file generated by OpenTofu
and one generated by real Terraform record different default registry
hostnames and are not interchangeable.

---

## 0. Prerequisites

- `gcloud` CLI, authenticated (`gcloud auth login`) as a user/account with
  Organization- or Billing-Account-level rights to create a new project.
  **On macOS, point it at Python ≥ 3.10** — the Xcode `python3` is 3.9 and
  makes `gcloud compute ssh` crash (`CommandLoadFailure … 'type' | 'NoneType'`);
  gcloud's own auto-installer needs sudo and can fail. Install the latest stable
  Python with Homebrew and pin it:
  `brew install python@3.13 && echo 'export CLOUDSDK_PYTHON=$(brew --prefix python@3.13)/bin/python3.13' >> ~/.zshrc`.
- `firebase` CLI (`npm install -g firebase-tools`), `firebase login`.
- `terraform` >= 1.6 (or `tofu` >= 1.6 — this module was authored and
  `validate`d with OpenTofu 1.12 against `hashicorp/google` 6.50.0).
- Node >= 22 and `pnpm` 11.1.1 locally if you want to run `pnpm build`
  before deploying, though `infra/vm/bootstrap.sh` and
  `infra/scripts/deploy.sh` also do this on the VM itself.

## Phase 0 — bootstrap, in order

### 0.1 Create a dedicated GCP project

docs/08 §8.1: this project holds **nothing else** — blast-radius isolation
for the one system that can move money.

```bash
gcloud projects create <PROJECT_ID> --name="Portfolio Manager"
gcloud billing projects link <PROJECT_ID> --billing-account=<BILLING_ACCOUNT_ID>
gcloud config set project <PROJECT_ID>
```

### 0.2 Enable the required APIs

Terraform's `infra/terraform/apis.tf` also declares these (so `terraform
apply` is idempotent even if you skip this step) — enabling them explicitly
first avoids ordering surprises, since Terraform itself needs
`cloudresourcemanager`/`iam` active to manage IAM at all.

```bash
gcloud services enable \
  compute.googleapis.com \
  firestore.googleapis.com \
  secretmanager.googleapis.com \
  cloudfunctions.googleapis.com \
  cloudscheduler.googleapis.com \
  run.googleapis.com \
  logging.googleapis.com \
  monitoring.googleapis.com \
  iam.googleapis.com \
  cloudresourcemanager.googleapis.com \
  firebase.googleapis.com \
  cloudbuild.googleapis.com \
  artifactregistry.googleapis.com \
  eventarc.googleapis.com \
  iamcredentials.googleapis.com \
  --project=<PROJECT_ID>
```

### 0.3 Firebase: enable + Auth providers + FCM

```bash
firebase projects:addfirebase <PROJECT_ID>
firebase use --add   # pick <PROJECT_ID>, alias it "default" — this rewrites .firebaserc locally; do not commit a real project id over the placeholder without checking docs/00 §0.7
```

Then in the [Firebase console](https://console.firebase.google.com/) →
your project:

- **Authentication → Sign-in method**: enable **Google** and **Apple**
  (docs/06 mobile app; docs/08 §8.1). Apple needs a Services ID + key from
  the Apple Developer portal — out of scope for this infra doc.
- **Cloud Messaging**: no separate "enable" step — it's available once
  Firebase is added; note the Sender ID/Server key for the mobile app.

### 0.4 Terraform: VM, static IP, service accounts, secrets, alerts, Firestore

```bash
cd infra/terraform
terraform init
cp terraform.tfvars.example terraform.tfvars
# edit terraform.tfvars: project_id, domain, allowed_uids, alert_email, ...
terraform plan
terraform apply
```

This is also where the **Firestore Native database in `asia-south1`** gets
created (`firestore.tf`'s `google_firestore_database`), along with its
7-day-retention backup schedule and the GCS export bucket. Firestore permits
exactly one default database per project, so if the database **already
exists** (created earlier with `gcloud firestore databases create` or in the
Firebase console — e.g. to deploy rules before the VM), `terraform apply`
fails with "database already exists". Adopt it into state once instead of
recreating it:

```bash
terraform import google_firestore_database.this "projects/<PROJECT_ID>/databases/(default)"
terraform plan   # expect only in-place updates on the database (delete protection, etc.), never a replace
```

(Firebase being "enabled" on the project in 0.3 does not itself create a
Firestore database, so there's no ordering conflict either way — the two are
independent GCP-level concerns.)

Note the outputs — you need `static_ip` for the next two steps:

```bash
terraform output static_ip
terraform output vm_name
```

### 0.5 Add secret VALUES (Terraform only creates empty secret shells)

Every secret id below is created by `secrets.tf` with **no version** —
add the real value once, interactively, so it never touches your shell
history or a file on disk longer than necessary:

```bash
# Backend — order-capable secrets (see the full table in §2 below)
printf '%s' '<DHAN_API_KEY>'      | gcloud secrets versions add dhan-api-key      --project=<PROJECT_ID> --data-file=-
printf '%s' '<DHAN_API_SECRET>'   | gcloud secrets versions add dhan-api-secret   --project=<PROJECT_ID> --data-file=-
printf '%s' '<DHAN_CLIENT_ID>'    | gcloud secrets versions add dhan-client-id    --project=<PROJECT_ID> --data-file=-
printf '%s' '<KITE_API_KEY>'      | gcloud secrets versions add kite-api-key      --project=<PROJECT_ID> --data-file=-
printf '%s' '<KITE_API_SECRET>'   | gcloud secrets versions add kite-api-secret   --project=<PROJECT_ID> --data-file=-
```

`dhan-access-token` / `kite-access-token` are populated by the backend
itself after the first daily login exchange (`POST
/v1/auth/:broker/callback` — docs/04) — you do not seed these by hand
under normal operation. If you need to for a first smoke test in `dry-run`
mode, any non-empty placeholder string works since dry-run never calls a
real broker endpoint.

The strategy engine's **read-only** credentials bundle is a single JSON
document, not four separate secrets — build it locally, pipe it in, then
delete the local file:

```bash
cat > /tmp/pm-strategy-creds.json <<'EOF'
{"broker":"dhan","dhan":{"clientId":"<DHAN_CLIENT_ID>","accessToken":"<READ_ONLY_ACCESS_TOKEN>","expiresAt":"2026-01-01T00:00:00.000Z"}}
EOF
gcloud secrets versions add pm-strategy-read-creds --project=<PROJECT_ID> --data-file=/tmp/pm-strategy-creds.json
shred -u /tmp/pm-strategy-creds.json   # or: rm -f /tmp/pm-strategy-creds.json
```

(For Kite instead: `{"broker":"kite","kite":{"apiKey":"...","accessToken":"...","expiresAt":"..."}}`.)

### 0.6 Whitelist the static IP with each broker

```bash
terraform -chdir=infra/terraform output -raw static_ip
```

- **Dhan**: developer portal → your app → **Whitelisted IPs** → add the IP.
  Dhan supports multiple whitelisted IPs, which is what makes
  `enable_staging_vm=true`'s separate IP safe to test with later.
- **Kite**: developer console → your app → whitelist. Kite allows **one IP
  per app** — testing a second (staging) IP means temporarily swapping it
  or using a second Kite app registration.

### 0.7 DNS

Point an A record for `<DOMAIN>` (matching `terraform.tfvars`'s `domain`)
at the `static_ip` output. Caddy's automatic HTTPS (ACME HTTP-01) needs
this to resolve **before** the VM's first boot, or the certificate request
fails (Caddy retries with backoff, so it self-heals once DNS propagates —
but don't expect HTTPS to work in the first few minutes after a DNS change).

### 0.8 First boot / `bootstrap.sh`

`infra/terraform/vm.tf` already wires `infra/vm/bootstrap.sh` in as the
instance's `metadata_startup_script`, so it runs automatically on first
boot (and every subsequent boot — it's idempotent, see the script's own
header comment). To watch it or re-run it by hand:

```bash
gcloud compute ssh <VM_NAME> --project=<PROJECT_ID> --zone=asia-south1-a --tunnel-through-iap
sudo journalctl -u google-startup-scripts -f     # watch first-boot progress
sudo bash /opt/pm/infra/vm/bootstrap.sh           # safe to re-run by hand
```

### 0.9 Fill in `/etc/pm/backend.env` and `/etc/pm/strategy.env`

`bootstrap.sh` seeds both files from `infra/vm/env/*.example` on first boot
(only if absent — it never overwrites a file you've already edited) and
best-effort fills `GCP_PROJECT`, `FIREBASE_PROJECT_ID`, `ALLOWED_UIDS`, and
`STATIC_IP` in `backend.env` from instance metadata / the VM's own assigned
IP. You still need to SSH in and set, at minimum:

```bash
sudo nano /etc/pm/backend.env    # ENVIRONMENT (start with dry-run!), MARKET_HOLIDAYS
sudo nano /etc/pm/strategy.env   # PM_UID, PM_BROKER_SECRET (full resource name — see comment in the file), PM_INSTRUMENTS_URL, PM_HOLIDAYS
sudo systemctl restart pm-backend pm-strategy
```

`PM_BROKER_SECRET` is the strategy engine's one required secret reference,
and it must be the **full** Secret Manager resource name, not a bare id:

```
projects/<PROJECT_NUMBER_OR_ID>/secrets/pm-strategy-read-creds/versions/latest
```

### 0.10 `firebase deploy` (rules, indexes, functions, TTL policies)

```bash
bash infra/scripts/firebase-deploy.sh <PROJECT_ID>
```

Runs `firebase deploy --only firestore:rules,firestore:indexes,functions`
then applies the two TTL field policies from `functions/README.md` that
`firebase deploy` never touches (`proposals.ttlExpiresAt`,
`idempotency.createdAt`).

> **Spark vs Blaze:** rules and indexes deploy on the free Spark plan. Cloud
> Functions and the TTL policies are rejected with "billing disabled" until the
> project is on Blaze — deploy `firestore:rules,firestore:indexes` alone in the
> meantime (that is what a Spark project can run).

Then provision the **operator-owned Firestore documents** for your user. The
rules forbid the app from *creating* `config`, `users`, `books`,
`strategies/defs` and `brokerSessions` (docs/03 §3.9), so an operator seeds them
once with the Admin SDK. Sign in to the app first, read your uid from
Authentication → Users, then:

```bash
cd apps/strategy
# inspect first (no writes, no auth needed)
GOOGLE_CLOUD_QUOTA_PROJECT=<PROJECT_ID> pnpm exec tsx scripts/seed-user.ts \
  --project <PROJECT_ID> --uid <FIREBASE_UID> --email <YOUR_EMAIL> --dry-run
# then write (uses Application Default Credentials)
GOOGLE_CLOUD_QUOTA_PROJECT=<PROJECT_ID> pnpm exec tsx scripts/seed-user.ts \
  --project <PROJECT_ID> --uid <FIREBASE_UID> --email <YOUR_EMAIL>
```

The script validates every document against the same zod schemas the app,
backend and strategy engine read (including each strategy's own params
schema), and uses `create()` so it refuses to overwrite live documents
(`--force` reseeds deliberately). The seeded state is inert by design:
`environment=dry-run`, `tradingEnabled=false`, every strategy disabled,
₹10k/order cap — you turn things on from the app.

### 0.11 Smoke test

```bash
bash infra/scripts/smoke.sh https://<DOMAIN>
```

Checks the public `/health` route; prints instructions for minting a test
Firebase ID token to also check the authenticated `GET /v1/session` route

| `kite-api-key` | Kite API key | pm-backend | — (operator, manual) | `KITE_API_KEY_SECRET` |
| `kite-api-secret` | Kite API secret | pm-backend | — (operator, manual) | `KITE_API_SECRET_SECRET` |
| `kite-access-token` | Kite daily access token | pm-backend | pm-backend (daily, automatic) | `KITE_ACCESS_TOKEN_SECRET` |
| `pm-strategy-read-creds` | READ-only `BrokerCreds` JSON (`{broker, dhan\|kite:{...,accessToken,expiresAt}}`) | pm-strategy only | — (operator, manual) | `PM_BROKER_SECRET` (strategy.env — full resource name, not a bare id) |

Notes:

- There is **no** `fb-admin-backend`/`fb-admin-strategy` secret, even
  though docs/08 §8.5 lists one. The actual code
  (`apps/backend/src/index.ts`, `apps/strategy/src/index.ts`) initializes
  Firebase Admin with `applicationDefault()` and never reads a service
  -account JSON from Secret Manager or anywhere else — on a GCE VM, ADC
  resolves to the VM's attached service account via the metadata server
  automatically, so no downloadable key/secret is needed at all. This is
  **better** than the docs/08 table implies (one fewer long-lived
  credential to manage), not a gap — see §6 for the full cross-check.
- `dhan-access-token`/`kite-access-token` get `secretVersionAdder` in
  addition to `secretAccessor` for `pm-backend` (`iam.tf`) — the backend
  rewrites these itself after each daily login exchange
  (`apps/backend/src/services/session.ts`). No other secret gets that role.
- `pm-strategy` gets `secretAccessor` on `pm-strategy-read-creds` **only** —
  see `infra/terraform/iam.tf`'s long comment for the important caveat
  about which identity is actually live on the VM today.

## 3. Egress allowlist — what it does and doesn't guarantee

`infra/vm/nftables-strategy-egress.conf` + `egress-allowlist.sh` restrict
the `pm-strategy` OS user to: DNS, the GCE metadata server, and HTTPS to
exactly these hosts —

| Host | Why |
|---|---|
| `api.dhan.co` | Dhan REST API (reads AND order endpoints — see below) |
| `api.kite.trade` | Kite REST API + `/instruments` CSV (reads AND order endpoints) |
| `firestore.googleapis.com` | proposals/auditLog writes, config/strategy-def reads |
| `secretmanager.googleapis.com` | fetching `pm-strategy-read-creds` |
| `oauth2.googleapis.com` | credential/token refresh paths some google-auth flows use |
| `metadata.google.internal` | Application Default Credentials token fetch |

**Read this honestly, don't just trust the firewall**: Dhan and Kite serve
order-placement and read/data endpoints from the **same hostname**. This
firewall enforces *hosts*, not *paths* — it cannot distinguish "GET
holdings" from "POST place order" to the same IP over the same TLS
connection. The guarantee that `pm-strategy` never calls an order endpoint
comes from the **code/lint/policy layer** (docs/05 §5.1: `apps/strategy`
only ever imports `BrokerReadAdapter`/`createReadAdapter`, which has no
order methods on it at runtime, enforced by `eslint.config.js` +
`policy.test.ts`), not from this firewall. What the firewall *does*
guarantee, and it's real: `pm-strategy` cannot reach **any host outside
this fixed list** at all, including an attacker-controlled exfiltration
endpoint or a broker order endpoint that happened to live on a different,
unlisted hostname. Defense in depth, not a single silver bullet — see
docs/07 §7.3's own layered model.

The two nft sets are populated by resolving these hostnames every 10
minutes (`pm-egress-allowlist.timer`) since they're plain DNS names, not
fixed IPs. A resolution failure for one host drops just that host's
entries until the next successful cycle (fail closed: a temporary read
outage, never an open door) — see the comment block at the top of
`egress-allowlist.sh`.

---

### Why hostnames are also pinned in `/etc/hosts`

`api.dhan.co` and the Google APIs answer DNS from rotating CDN/anycast pools, so an
IP set filled from one lookup only matches a later lookup by luck; every miss was a
dropped connection and a strategy tick failing closed with `fetch failed`. Each
refresh therefore resolves through `host` (DNS only) and rewrites a managed block
in `/etc/hosts` pinning every allowlisted hostname to one of the addresses it just
put in the sets. Both units resolve through glibc, so they agree by construction.
The instrument masters no longer need a CDN host at all: the backend caches them
under `/var/lib/pm/instruments` and the engine reads them from there
(`PM_INSTRUMENTS_DIR`).

The chain matches the `pm-strategy` user *positively* and accepts established
connections: packets without a socket (the kernel's own RSTs) are not the engine's,
and a connection the engine was allowed to open must survive the next refresh — the
control is on opening connections, which is what an exfiltration attempt needs.

## 4. Incident playbook (docs/07 §7.8)

In order. Don't skip steps to save time — the order is chosen so each step
narrows the blast radius before the next one takes longer to complete.

### 1. Kill switch

If the backend is reachable:

```bash
curl -X POST "https://<DOMAIN>/v1/config/killswitch" \
  -H "Authorization: Bearer <YOUR_FIREBASE_ID_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true, "reason": "incident: <one line>"}'
```

(Minting `<YOUR_FIREBASE_ID_TOKEN>`: same Firebase Auth REST API call
documented in `infra/scripts/smoke.sh`'s output — use your own account,
not a test user, during a real incident.)

If the backend is **not** reachable, the fail-closed design means it
already refuses all orders (docs/07 §7.8: "if the backend can't read
config, it refuses") — there is nothing further to do here, but flip the
Firestore `config/{uid}.killSwitch` field to `true` directly via the
Firebase console anyway, so the moment the backend recovers it starts
back up already killed rather than racing you.

### 2. Revoke the broker token / rotate the secret

```bash
printf '%s' '<NEW_VALUE>' > /tmp/rotate.txt
infra/scripts/rotate-broker-key.sh dhan-access-token /tmp/rotate.txt --project=<PROJECT_ID>
# or kite-access-token, or the long-lived dhan-api-key/dhan-api-secret/kite-api-key/kite-api-secret
# if you suspect those (not just the daily token) were exposed.
shred -u /tmp/rotate.txt
```

Also revoke the token broker-side if the broker's developer portal offers
a "revoke session" action — Secret Manager rotation alone only stops
*this system* from using the old token; it doesn't invalidate it at the
broker.

### 3. Remove the IP from the broker's whitelist, if the VM itself is compromised

There is **no API for this** — confirmed by
`apps/backend/src/http/app.ts`'s `/v1/admin/whitelist-ip` route, which
deliberately answers `501 NOT_IMPLEMENTED` because neither broker exposes
a programmatic whitelist endpoint. Do it by hand: Dhan developer portal →
app → Whitelisted IPs → remove; Kite developer console → app → whitelist →
remove. This is the point at which the account cannot place orders through
this system **at all** until you whitelist a (new) IP again — the most
drastic, most effective containment step.

### 4. Review the audit log

`auditLog` is append-only and client-unwritable (docs/07 §7.7). Query it
via the Firestore console (Firestore → Data → `auditLog`, filter by `uid`
and `ts` range) or `gcloud firestore` if you've scripted a query tool —
there's no bundled CLI for this in `infra/scripts/` today (out of scope
for this module; consider it a documented gap, not an oversight).

### 5. Reconcile with the broker

Reconciliation runs automatically every `RECONCILE_INTERVAL_MS` (default
15s, `backend.env`) — there is no manual-trigger endpoint. During an
incident, cross-check the broker's own order/trade book (portal UI) against
Firestore's `orders` collection for the affected `uid` and time window, and
watch Cloud Logging for `reconcile`-tagged log lines
(`journalctl -u pm-backend | grep reconcile` on the VM, or Logs Explorer).

### 6. Post-mortem

Not automatable — write down what happened, when, what the audit log
shows, and what changes (config, code, or process) would have caught it
sooner. Feed anything code-shaped back into `docs/11`'s VERIFY-LIVE list if
it turns out to be a wrong wire-format assumption.

## 5. Backup / restore

**Firestore** — two independent mechanisms (`infra/terraform/firestore.tf`):

- Managed daily backups (`google_firestore_backup_schedule`, 7-day
  retention) — restore with:
  ```bash
  gcloud firestore backups list --project=<PROJECT_ID>
  gcloud firestore databases restore --source-backup=<BACKUP_NAME> \
    --destination-database='(default)' --project=<PROJECT_ID>
  ```
  (Restoring over the live `(default)` database is destructive — check the
  current `gcloud` docs for whether your version requires restoring to a
  *new* database id first and then swapping over.)
- Ad-hoc/manual portable export to the GCS bucket
  (`<PROJECT_ID>-firestore-backups`, 30-day lifecycle) — this bucket is
  provisioned but nothing schedules exports into it automatically (see the
  comment in `firestore.tf`); run by hand before anything risky:
  ```bash
  gcloud firestore export gs://<PROJECT_ID>-firestore-backups/manual-$(date +%Y%m%d) --project=<PROJECT_ID>
  gcloud firestore import gs://<PROJECT_ID>-firestore-backups/<export-path> --project=<PROJECT_ID>
  ```

**VM** — daily boot-disk snapshot (`google_compute_resource_policy`,
7-day retention, `vm.tf`):

```bash
gcloud compute snapshots list --project=<PROJECT_ID>
gcloud compute disks create pm-backend-boot-restored \
  --source-snapshot=<SNAPSHOT_NAME> --zone=asia-south1-a --project=<PROJECT_ID>
# then either attach it to a new instance, or stop the VM and swap its boot disk.
```

## 5. Optional operating window (off by default — the VM is always on)

By default the VM runs 24/7. Setting `vm_schedule_enabled = true` in
`terraform.tfvars` attaches a Compute Engine instance schedule (`Asia/Kolkata`):
**start 07:15 IST, stop 16:15 IST, Mon–Fri** (`vm_start_cron` / `vm_stop_cron`) —
two hours of pre-market before the 09:15 open and a 45-minute buffer after the
15:30 close for the 15:45 eod tick and the reconcile loop. It was evaluated for
this deployment and left off: it saves only ~₹230/month (docs/08 §8.9).

If you do enable it, this is what changes operationally:

- **Deploys are explicit.** `bootstrap.sh` clones and builds on the *first* boot
  only; on every scheduled start it re-installs units/configs and starts the
  services but never touches the checkout. Ship code with `infra/scripts/deploy.sh`.
- **Health is checked in-window, not 24/7.** A Cloud Scheduler job pings
  `https://<DOMAIN>/health` at 07:45 IST; its failure raises the
  "pm-backend not up during trading window" alert. The 24/7 uptime check only
  exists when `vm_schedule_enabled = false`.
- **Holidays are not excluded.** The VM also runs on NSE holidays that fall on a
  weekday (~$0.10/month); the strategy engine no-ops on them via `PM_HOLIDAYS`.
- **The static IP costs more while the VM is off** (unused reserved IP: $0.01/h vs
  $0.005/h in use) and must stay reserved — it is the whitelisted address. Net
  saving vs always-on is ~₹230/month; the window is about the operating envelope
  more than cost (docs/08 §8.9).
- **Applying Terraform while the VM is stopped** (off-hours) is fine; the provider
  does not force a start. To run outside the window (an incident, a manual test):
  `gcloud compute instances start pm-backend-vm --zone asia-south1-a` — the next
  scheduled stop will still shut it down.
- **Requires** `roles/compute.instanceAdmin.v1` on the Compute Engine service agent
  (granted in `iam.tf`) — without it the schedule silently never fires. Verify on
  day 1 (docs/11 §11.6 #9).
